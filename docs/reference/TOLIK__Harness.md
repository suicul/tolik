# TOLIK — архитектурная модель и целевое поведение
## Техническое задание для DeepSeek Harness

> Этот документ объясняет, как модули TOLIK должны быть связаны и работать вместе. Это не разрешение переписать проект. Сначала исследуй репозиторий, построй карту реального исполнения и покажи расхождения. Не считай описанные возможности реализованными без подтверждения кодом и тестами.

## 0. Главная задача

Ты должен понять TOLIK как **единую персональную цифровую систему с одной идентичностью и одним активным Core**, а не как набор независимых приложений или LLM-обёртку.

Текущая фаза проекта — PRE-GENESIS hardening: последовательное закрытие проблем безопасности, целостности памяти, восстановления и жизненного цикла до READY_FOR_GENESIS. Не расширяй функциональность и не начинай крупный рефакторинг до архитектурного аудита и согласования плана.

Для каждого свойства используй статус:
- `IMPLEMENTED` — подтверждено реализацией и релевантными тестами;
- `PARTIAL` — есть реализация, но не закрыты важные сценарии;
- `MISSING` — не найдено;
- `UNVERIFIED` — нельзя подтвердить;
- `CONFLICT` — реализация нарушает архитектурный инвариант.

Интерфейс, DTO, комментарий или заглушка не доказывают, что функция работает.

---

# 1. Что такое TOLIK

**TOLIK — одна непрерывная персональная цифровая система, которая сохраняет идентичность и историю, воспринимает контекст, рассуждает через сменные модели, принимает решения через контролируемое ядро и выполняет разрешённые действия через специализированные исполнительные узлы.**

Толик не равен:
- LLM или конкретному провайдеру;
- приложению или пользовательскому интерфейсу;
- Windows-процессу или VPS;
- Agent на конкретном устройстве;
- голосовому контуру.

Главные инварианты:

1. **Одна Identity.**
2. **Один активный Core.**
3. Много подключённых клиентов, устройств, сенсоров и Agent.
4. LLM — заменяемый интеллектуальный провайдер, не корень доверия.
5. Core управляет состоянием, памятью, задачами и маршрутизацией.
6. Security независимо определяет, что разрешено.
7. Agent исполняет только адресованные ему разрешённые операции.
8. Клиенты обеспечивают присутствие и взаимодействие, но не обладают властью Core.

Не допускай split-brain: два Core не должны одновременно принимать команды и независимо менять каноническое состояние. Для этого требуется lease/epoch/fencing или эквивалентный проверяемый механизм.

# 2. Ментальная модель: полный цикл

Правильная последовательность:

1. Клиент или сенсор получает событие: текст, звук, команду или состояние устройства.
2. Событие поступает в Core по аутентифицированному каналу.
3. Core устанавливает источник, сессию и, если нужно, говорящего.
4. Core получает подходящий контекст Identity и Memory с учётом scope и приватности.
5. Attention/Intent определяет, нужно ли реагировать и что хочет пользователь.
6. Planner формирует возможный план.
7. Security проверяет полномочия, ресурс, действие, риск и необходимость подтверждения.
8. Model Router выбирает LLM для интеллектуальной работы и передаёт ей только необходимый контекст.
9. Core проверяет результат модели и превращает его в валидированную задачу/команду.
10. Agent получает конкретную команду и проверяет её подлинность, срок, epoch и capabilities.
11. Agent выполняет разрешённую операцию на устройстве.
12. Core проверяет результат, обновляет состояние задачи, записывает аудит и при необходимости память.
13. Клиенты получают обновление; голосовой контур может озвучить ответ.

Ключевая формула:

**Модель предлагает → Core проверяет → Security разрешает → Agent исполняет → Core проверяет результат.**

Запрещённые сокращения:
- `LLM → Shell`;
- `Client → Agent` в обход Core;
- `LLM → database` напрямую;
- Agent самостоятельно выдаёт себе права;
- результат Agent автоматически считается достоверным и успешным.

# 3. Границы ответственности модулей

Фактические названия проектов могут отличаться. Найди реальные проекты, зависимости, точки входа и вызовы. Ниже — целевые обязанности.

## 3.1 Contracts

Общие контракты: DTO, команды, события, task models, Agent Protocol, версии протокола, типизированные ответы.

Не содержит бизнес-решений, доступа к ОС, реализации БД, выбора модели и авторизации.

Контракты должны быть версионируемыми, однозначными и проверяемыми.

## 3.2 Core — центральный орган управления

Core — не просто API-прокси. Это единственный авторитетный центр TOLIK.

Ответственность Core:
- Identity и lifecycle state;
- owner binding и пользовательские роли;
- сессии и контекст;
- каноническое состояние задач;
- координация Memory;
- Attention, Intent, Planner и orchestration;
- Model Router;
- Security/Authorization enforcement;
- управление Agent и устройствами;
- подтверждения критичных действий;
- обработка событий и уведомления клиентов;
- аудит значимых операций;
- координация голосового и иных каналов.

Core является источником истины для `instance_id`, owner binding, lifecycle, активных полномочий, task state, зарегистрированных Agent, подтверждений и канонической памяти.

Core может делегировать вычисление модели и исполнение операций, но не делегирует Identity и Authorization.

## 3.3 Infrastructure

Технические реализации интерфейсов Core:
- PostgreSQL repositories;
- транспорт;
- LLM API clients;
- файловое/объектное хранилище;
- очереди и фоновые механизмы;
- криптография, секреты и внешние адаптеры.

Infrastructure не решает, разрешено ли действие. Она исполняет технические операции по запросу доменного слоя.

## 3.4 Host

Composition root и точка запуска:
- DI;
- конфигурация и секреты;
- регистрация зависимостей;
- HTTP/WebSocket endpoints;
- hosted services;
- безопасные startup/shutdown;
- health checks.

Host не должен становиться вторым Core или содержать дублирующую бизнес-логику.

## 3.5 Agent — исполнитель устройства

Agent зарегистрирован в Core и действует в пределах ограниченных capabilities.

Ответственность:
- аутентифицированное подключение и enrollment;
- heartbeat, health и capabilities;
- получение адресованных команд;
- проверка подписи/подлинности, срока, task ID, agent ID, epoch и локальных ограничений;
- выполнение разрешённых OS-операций;
- структурированный результат, progress и ошибки;
- корректная остановка/отказ при отзыве полномочий или устаревшей команде.

Agent может читать/записывать разрешённые файлы, запускать определённые процессы, собирать логи, выполнять build/test, взаимодействовать с приложениями и запускать dev-агентов — только если эти capabilities явно выданы.

Agent не может:
- определять владельца TOLIK;
- менять Identity или lifecycle;
- самостоятельно расширять capabilities;
- напрямую менять canonical memory;
- считать вывод LLM разрешением;
- выполнять произвольный shell по факту сетевого сообщения;
- обходить Core;
- продолжать критичное действие с просроченным разрешением.

Core и Agent могут физически работать на одном Windows-ПК, но это разные логические роли с разными полномочиями.

## 3.6 Clients — интерфейсы присутствия

Windows UI, Linux, Android, web/desktop и будущий VR-клиент:
- принимают текст/голос/ввод;
- отображают состояние;
- показывают подтверждения;
- передают запросы Core;
- получают события и ответы;
- управляют локальным UX.

Клиент не авторизует действия, не является владельцем памяти, не назначает Agent и не может менять lifecycle. Linux и Android в целевой модели — преимущественно тонкие клиенты.

# 4. Топология развёртывания

Целевой вариант:

```text
                  ┌─────────────────────────────┐
                  │          TOLIK CORE         │
                  │ Identity / Memory / Tasks  │
                  │ Planner / Model Router     │
                  │ Security / Audit / Events  │
                  └──────────────┬──────────────┘
                                 │
                 ┌───────────────┼────────────────┐
                 │               │                │
             Client API      Agent Protocol    Model APIs
                 │               │                │
          ┌──────┴──────┐   ┌────┴─────┐    ┌─────┴─────┐
          │ Android    │   │ Windows  │    │ Cloud /   │
          │ Linux      │   │ Agent    │    │ Local LLM │
          │ UI         │   │ Tools    │    └───────────┘
          └─────────────┘   └──────────┘
```

Домашний Windows-ПК может запускать Core и Windows Agent. В будущем Core может переехать на Linux VPS, а домашний Windows Agent останется исполнителем. Linux-ноутбук и Android подключаются к тому же Core. Физическое размещение не меняет логические границы.

## 4.1 Core lease / epoch / fencing

Нужна гарантия единственного активного Core:
- lease с ограниченным сроком;
- монотонный epoch/generation;
- новый Core получает новый epoch только после безопасного перехода;
- Agent и хранилище отклоняют команды старого epoch;
- старый Core теряет возможность записи/dispatch;
- сетевое разделение не создаёт два активных центра.

Один флаг `IsPrimary` не является достаточной гарантией.

## 4.2 Миграция Core

Целевой процесс:
1. PREPARE: проверить целевой хост, версии, БД, конфигурацию и секреты.
2. Зафиксировать активный Core и epoch.
3. Создать согласованный snapshot и синхронизировать последующие изменения.
4. Проверить целостность snapshot и backup.
5. Запустить новый Core в неактивном режиме.
6. Пройти health checks.
7. Атомарно выдать новому Core новый epoch/lease.
8. Переподключить Agent и клиентов.
9. Fencing старого Core.
10. Проверить отсутствие дублей задач и конфликтующих операций.

Никогда не допускай параллельного активного исполнения двух Core.

# 5. Сквозной пример: «Проверь проект и запусти тесты»

1. Клиент отправляет запрос Core.
2. Core аутентифицирует клиента и связывает запрос с сессией.
3. Core проверяет идентичность говорящего, если это голосовой канал. Speaker ID не заменяет authentication.
4. Core извлекает нужный контекст памяти и проекта.
5. Intent определяет запрос как задачу анализа/тестирования.
6. Planner формирует план: определить репозиторий, изучить состояние, выбрать тесты, выполнить и проанализировать результат.
7. Security проверяет роль, scope, capabilities и риск.
8. Model Router выбирает подходящую модель для анализа.
9. Core валидирует план модели; модель не может назначить себе права.
10. Core создаёт Task с ID, состоянием и критериями успеха.
11. Core отправляет Agent команду с task ID, agent ID, epoch, сроком действия, correlation/idempotency ID и ограниченным authorization context.
12. Agent проверяет команду и локальные ограничения.
13. Agent запускает разрешённые тесты.
14. Agent возвращает exit code, stdout/stderr или ссылки на логи, duration и изменения файлов.
15. Core проверяет свежесть и принадлежность результата задаче.
16. Core обновляет task state; при необходимости LLM анализирует логи.
17. Core пишет аудит, сохраняет только значимые сведения в соответствующий memory scope.
18. Клиент получает итог.

Не допускай `LLM → shell` и не считай текст «тесты прошли» доказательством реального выполнения.

# 6. Task Manager и оркестрация

Task Manager принадлежит Core. Задача — долговечная сущность, а не одно сообщение чата.

Минимальные атрибуты:
- task ID;
- инициатор/источник;
- цель и критерии успеха;
- статус и этапы;
- назначенный Agent/инструмент;
- authorization context;
- timestamps;
- correlation/idempotency IDs;
- подтверждения;
- результаты, ошибки и ссылки на аудит.

Возможный жизненный цикл (сверь с существующими enum):
`Created → Planned → AwaitingAuthorization/Confirmation → Authorized → Dispatched → Running → Verifying → Completed`.

Альтернативные исходы: `Rejected`, `Cancelled`, `Failed`, `TimedOut`, `Interrupted`, `NeedsHuman`.

Требования:
- повторная доставка не повторяет неидемпотентное действие;
- cancellation и timeout имеют определённую семантику;
- progress и heartbeat отражаются в Core;
- после падения Core нельзя слепо повторять команду: сначала выясни, выполнил ли её Agent;
- состояние задачи переживает рестарт;
- результат связывается с исходной задачей и конкретным Agent.

# 7. Identity и Genesis

Identity — структурированная постоянная сущность, а не только system prompt. В неё входят `instance_id`, owner binding, принципы, устойчивый профиль, роли/отношения, lifecycle и ссылки на подтверждённую историю.

Канонический lifecycle:

```text
DEVELOPMENT
    ↓
PRE-GENESIS
    ↓
READY_FOR_GENESIS
    ↓
GENESIS (однократно)
    ↓
LIFETIME
```

- `DEVELOPMENT`: разработка и эксперименты; данные не являются lived memory.
- `PRE-GENESIS`: hardening, аудит, тесты безопасности и восстановления.
- `READY_FOR_GENESIS`: все обязательные критерии готовы и зафиксированы.
- `GENESIS`: контролируемое создание постоянного экземпляра и owner binding.
- `LIFETIME`: постоянная эксплуатация.

Genesis — не обычный startup и не API reset. Он должен:
1. Разрешаться только из READY_FOR_GENESIS.
2. Требовать подтверждённую авторизацию владельца и MFA/step-up согласно политике.
3. Создать `instance_id` и owner binding.
4. Проверить начальную конфигурацию и разделение памяти.
5. Записать событие в audit.
6. Атомарно перевести lifecycle в LIFETIME.
7. Не допустить двух Identity при сбое/повторном запросе.

После LIFETIME обычные runtime-пути не могут делать reset личности, повторный bootstrap/Genesis, замену владельца, тихое удаление audit или отключение обязательных security controls. Исправление и удаление пользовательских данных — отдельные авторизованные и аудируемые процессы, не reset личности.

## PRE-GENESIS checklist

Проверь:
- целостность конфигурации и схемы БД;
- проверенный backup и успешный restore drill;
- owner authentication;
- MFA/step-up для критичных операций;
- реальные authorization enforcement points;
- разделение memory origins/scopes;
- защиту секретов и данных at rest;
- audit integrity;
- durable confirmations;
- поведение при потере сети и падении Core;
- отсутствие dev-only токенов/обходов в production path;
- отрицательные lifecycle/security tests;
- блокировку повторного Genesis и re-bootstrap.

# 8. Memory: происхождение, scope и поток данных

PostgreSQL — каноническое хранилище постоянной памяти, если это подтверждается реализацией. LLM может предложить запись или summary, но не должна напрямую записывать произвольные утверждения в permanent memory.

Различай **origin** и **type**.

Origins/scopes:
- `development` — тесты, отладка, экспериментальные разговоры;
- `imported` — импортированные документы и внешние источники;
- `lived` — подтверждённые события реального взаимодействия после Genesis;
- `system` — техническое состояние/конфигурация;
- `audit` — защищённая история значимых действий.

Типы могут включать:
- episodic — события;
- semantic — устойчивые факты;
- working — временный контекст;
- procedural — проверенные способы выполнения действий.

Пример: факт из импортированного документа может быть semantic knowledge, но его origin остаётся `imported`, а не `lived`.

Значимая запись должна иметь:
- provenance/source;
- timestamp;
- subject/owner и scope;
- confidence/verification status;
- ссылку на исходное событие/документ;
- версию/историю исправлений;
- правила доступа/retention.

## Поток записи

1. Событие поступает в Core.
2. Core проверяет источник, пользователя и доступ.
3. Memory pipeline решает, стоит ли сохранять.
4. Запись получает origin, type и scope.
5. Сохраняется provenance и статус подтверждения.
6. Применяются privacy/retention policies.
7. Core сохраняет запись и связь с исходным событием.
8. При извлечении Core фильтрует данные по пользователю, scope и origin.

Не считай последнее сообщение автоматически истинным. Исправления меняют canonical view, но история исправления остаётся аудируемой. Compaction не должна терять даты, участников, причинность, provenance или превращать предположение в факт. Development/imported не переходят автоматически в lived.

# 9. Security — отдельная плоскость управления

Не смешивай:
- Authentication — кто установил соединение?
- Ownership — является ли он владельцем экземпляра?
- Authorization — разрешено ли именно это действие над этим ресурсом сейчас?
- Confirmation — подтвердил ли человек конкретное действие?
- MFA/step-up — прошёл ли усиленную проверку?

Последовательность:

```text
WHO?
  ↓
AUTHENTICATED?
  ↓
OWNER / ROLE?
  ↓
ACTION + RESOURCE + SCOPE AUTHORIZED?
  ↓
RISK POLICY
  ↓
MFA / EXPLICIT CONFIRMATION (if required)
  ↓
SHORT-LIVED EXECUTION GRANT
  ↓
AGENT VALIDATION
  ↓
EXECUTE
  ↓
AUDIT + RESULT VERIFICATION
```

Недоверенные источники:
- LLM output и планы Planner;
- документы, веб-страницы и tool output;
- клиентские payloads;
- результаты Agent до проверки.

JSON/schema validation не равна authorization.

Каждое исполнение должно быть ограничено конкретным действием, ресурсом, scope и сроком, связано с инициатором/task ID, отзываться и проверяться. Никаких универсальных бессрочных токенов Agent.

Подтверждение:
- durable, не только в RAM;
- связано с точным payload операции;
- не переиспользуется для другого действия;
- критичные действия требуют MFA/step-up по политике.

Если MFA не реализована — пометь `MISSING/PARTIAL`, не подменяй её обычной сессией.

Audit фиксирует enrollment, auth, выдачу/отзыв прав, подтверждения, dispatch/result, изменения Identity/lifecycle/memory, backup/restore, миграции и lockdown. Hash-chain полезна, но сама по себе не гарантирует абсолютную неизменяемость: учитывай защиту ключей и независимые anchors/copies.

# 10. Agent Protocol и транспорт

Проверь реальную реализацию. В целевой модели WebSocket — основной realtime канал, HTTP fallback допустим; нужны reconnect, heartbeat и события.

Сообщение протокола должно включать:
- protocol version;
- message ID;
- correlation ID;
- task ID;
- agent ID;
- Core epoch;
- timestamp/expiry;
- message type и schema;
- authentication/integrity metadata.

Типы сообщений могут включать:
`AgentHello`, `EnrollmentRequest`, `EnrollmentAccepted`, `Heartbeat`, `CapabilitiesReport`, `TaskDispatch`, `TaskAccepted`, `TaskProgress`, `TaskResult`, `TaskFailed`, `TaskCancel`, `AgentHealth`, `Revoke`.

Нужны аутентификация транспорта, replay protection, дедупликация, timeout, backpressure, protocol compatibility, reconnect, fencing и безопасная обработка устаревших команд.

Потеря связи не должна давать дополнительные права или автоматически разрешать опасную операцию.

---

# 11. Model Router и LLM

Model Router принадлежит Core и выбирает модель по:
- типу/сложности задачи;
- качеству;
- latency;
- стоимости;
- доступности;
- приватности;
- контекстному окну и поддерживаемым возможностям.

LLM может классифицировать намерение, извлекать данные, предлагать план, анализировать код/логи, писать ответ и предлагать memory candidates.

LLM не может выдавать права, менять владельца/lifecycle, писать в canonical DB напрямую, отправлять Agent-команды в обход Core, отменять подтверждение или отключать audit.

Core передаёт модели минимальный необходимый контекст. Не отправляй всю память, секреты и личные данные других пользователей без необходимости. При сбое провайдера Core сохраняет task state; fallback не должен ослаблять Security или повторять неидемпотентные действия.

---

# 12. Voice, сенсоры и Presence

Голос — канал восприятия и ответа единого Core, а не отдельный мозг или отдельная память.

Целевой поток:

```text
Microphone
  → VAD / segmentation
  → STT
  → Speaker ID + confidence
  → Addressing / Intent
  → Attention arbitration
  → Core context + Memory
  → Planner / Model Router
  → Security (if action)
  → Response
  → Voice Gate
  → TTS
  → DSP / playback
```

Разделяй понятия:
- Speaker ID — вероятностная оценка, кто говорит;
- Authentication — подтверждение цифровой личности;
- Attention — нужно ли реагировать сейчас;
- Authorization — разрешено ли действие;
- Emotion — лишь возможная оценка состояния, не факт.

Узнавание голоса само по себе не даёт права владельца и не заменяет MFA для критичных действий.

Voice Gate учитывает quiet mode, режим listen/process/speak, прерывания и состояние воспроизведения. Предотвращай самопрослушивание и циклы повторной активации через явное управление состояниями, echo cancellation/ducking или эквивалент.

Известные экспериментальные технологии: faster-whisper, CampPlus, CosyVoice 3, XTTS, NAudio. Проверяй текущий код; не считай эти библиотеки обязательными, если реализация изменилась.

Attention arbitration решает приоритет и момент реакции, но не выдаёт права. Presence описывает доступность/активность устройств, но не является Identity.

# 13. Supervisor, Recovery и self-maintenance

Supervisor/Health следит за Core, БД, Agent, транспортом и зависимостями, выявляет деградацию, собирает диагностику и запускает безопасные recovery procedures. «Процесс запущен» не означает `healthy`.

Recovery:
- использует проверенный snapshot, journal и checkpoints;
- проверяет целостность;
- учитывает epoch;
- восстанавливает незавершённые задачи;
- не повторяет вслепую неидемпотентные операции;
- при неопределённости требует человека.

Будущий self-maintenance pipeline:
`Analyze → isolated workspace/branch → dev-agent change → sandbox tests → diff/security review → backup → canary/staged deploy → health check → rollback if needed`.

Критичные компоненты Security, Identity, Genesis/Lifecycle, Authorization, Audit, Supervisor/Recovery нельзя менять и выкатывать автономно без отдельного одобрения владельца. Self-maintenance не может переписывать собственные ограничения или удалять следы изменений.

---

# 14. Backup, restore и миграция состояния

Различай operational state, memory, identity/lifecycle, authorization/confirmations, audit, configuration/secrets и task execution state.

Backup — не просто файл. Нужен успешный restore drill в изолированной среде. Восстановление должно определить:
- валидный snapshot;
- события после snapshot;
- текущий epoch;
- какие Agent-команды реально завершились;
- какие задачи можно продолжить;
- какие операции требуют сверки/вмешательства человека.

Важные подтверждения, задачи и lifecycle нельзя хранить только в RAM.

# 16. Анти-паттерны — архитектурные ошибки

1. `LLM → Shell` без Core authorization.
2. `Client → Agent` в обход Core.
3. Agent меняет Identity/lifecycle/permanent memory напрямую.
4. Подключение приравнивается к ownership.
5. Speaker ID используется вместо authentication/MFA.
6. Один модуль одновременно планирует, авторизует и исполняет.
7. System prompt считается единственным хранилищем личности.
8. На каждом устройстве независимая копия личности/памяти.
9. Два активных Core.
10. Confirmations только в RAM.
11. LLM получает всю память/секреты.
12. Результат Agent считается успешным без проверки.
13. Повторная доставка повторяет опасное действие.
14. Development/imported автоматически становится lived memory.
15. Genesis можно повторить обычным API вызовом.
16. Reset/owner replacement/audit deletion доступны после LIFETIME.
17. Сбой сети автоматически ослабляет security.
18. Health check проверяет только факт запуска процесса.
19. README/комментарий принимается за доказательство реализации.
20. Массовый рефакторинг начинается до карты зависимостей и тестов.

После согласования делай небольшие изменения, добавляй тест на исходный риск, запускай релевантные тесты и затем полный набор.

# 19. Главная схема — запомни её

```text
DEVICES / CLIENTS / SENSORS
            │
            ▼
         TOLIK CORE
            │
            ├── Identity + Lifecycle
            ├── Memory + Provenance
            ├── Attention + Intent
            ├── Planner + Task Manager
            ├── Model Router ─────────► LLM PROVIDERS
            ├── Security + Authorization
            ├── Audit + Recovery
            │
            ▼
    AUTHORIZED TASK / COMMAND
            │
            ▼
          AGENT(S)
            │
            ▼
     OS / FILES / APPS / TOOLS
            │
            ▼
   STRUCTURED RESULT / EVENTS
            │
            ▼
         TOLIK CORE
            │
            ├── Verify result
            ├── Update task state
            ├── Persist allowed memory
            ├── Write audit
            └── Notify clients / voice output
```

**Core управляет состоянием и оркестрацией. Security решает, что разрешено. Model помогает рассуждать. Agent исполняет. Client обеспечивает присутствие. Memory сохраняет проверяемую историю. Identity обеспечивает непрерывность.**

Это базовая ментальная модель TOLIK. Любая предлагаемая архитектура должна ей соответствовать либо явно обосновывать, какой инвариант и почему меняется.
