## 1. Блокеры: что мешает эталону

Каждый пункт — проверяемый факт с адресом в коде, а не мнение.

### Б1. Церемония рожает личность, но не оживляет ум

`GenesisSeedRuntime.Load()` и `Activate()` **не вызываются в продакшене
ни разу**. Единственное обращение в `Program.cs` — чтение статуса:

```csharp
// src/TOLIK.Core.Host/Program.cs:237
status = mind.GenesisSeed.Status.ToString(),
```

`docs/genesis-ceremony.md` (Шаг 4 и Шаг 7) обещает, что после церемонии
`GET /mind/state` вернёт `"status":"Activated"` и ум начнёт читать seed.
В коде нет пути, который это сделает: статус навсегда останется `NotSeeded`.

Последствие: церемония пройдёт, вернёт `LIFETIME`, запишет audit-событие — и
не изменит поведение ума вообще. Это ровно тот «выдуманный отчёт», который
владелец запретил.

### Б2. Критические операции запрещены навсегда

При диспетчеризации MFA зашита константой:

```csharp
// src/TOLIK.Core.Host/Program.cs:1652
var decision = AuthorizationPolicy.Evaluate(new AuthorizationRequest(
    principal, capability, declaredRisk, resource, resource, confirmationValid, MfaValid: false,
    ...
```

А политика требует MFA для критического риска:

```csharp
// src/TOLIK.Infrastructure/Authorization/AuthorizationPolicy.cs:149
ToolRiskLevel.Critical => request.ConfirmationValid && request.MfaValid
    ? AuthorizationDecision.Allow : AuthorizationDecision.Deny,
```

Следствие: `AgentCapability.InstallTolikUpdate` (`CapabilityRegistry.cs:64`,
риск `Critical`) **не выполнится никогда** — даже с подтверждением и верным
TOTP-кодом. Самообновление TOLIK заблокировано по построению.

Важно: `RunCodex` и `RunOpenCode` имеют риск `Modify`, не `Critical` — их
этот дефект не блокирует. То есть «улучшать свой код» через Codex/OpenCode
можно уже сейчас; нельзя только устанавливать обновление себя.

### Б3. Ум не переживает перезапуск

```csharp
// src/TOLIK.Core/MindRuntime.cs:16
private readonly MindState _state = new();
```

Скука, любопытство, внимание, серия неудач — всё в памяти процесса. Рестарт
Core обнуляет внутреннюю жизнь. «Непрерывное существование» из
`docs/continuous-autonomy.md` в этой части не выполняется.

### Б4. Подтверждений нет в клиенте

Бэкенд готов: `GET /tasks/{taskId}/confirmations` и
`POST /tasks/{taskId}/confirmations/{confirmationId}/approve` существуют
(`Program.cs:1550`, `1562`). В Windows-клиенте подтверждений нет вообще —
поиск по `src/TOLIK.Desktop/**/*.xaml,*.cs` по слову `confirm` не даёт
совпадений.

Следствие: любое действие уровня `Modify` и выше упирается в тупик —
Core возвращает «требуется подтверждение», а подтвердить нечем, кроме ручного
вызова API. Лестница рисков работает только до `LowRisk`.

### Б5. Документы противоречат решению владельца

`docs/post-genesis-roadmap.md` относит к post-genesis: Android, vision,
desktop embodiment, pgvector, VPS. Решение idx=2437 переносит почти всё это
в pre-genesis.

### Б6. Контекстный документ устарел на месяц

`docs/ТЕКУЩИЙ-КОНТЕКСТ.md` датирован 02.10.2026 и говорит про 232 теста.
Сегодня их 880 + 305. Документ, который советуют читать первым, врёт.

### Б7. Много построено, но не подключено

По итогам аудита: `ConsentModel`, `TrustProfile`, `RewardStore`,
`ExperimentLab`, `MetricRecorder`, `OptimizationBudget`, `RecoveryPolicy`,
`WaitUntil`, `SelfModelBuilder`, `SelectionInspector` имеют ноль вызовов в
продакшене — только тесты. Это не мусор: это фундамент, у которого нет
потребителя. Каждый нужно либо подключить к реальному пути, либо честно
пометить как задел.

## 2. Маршрут TDD

- **Режим:** `auto`
- **Решение:** `strict` для Фаз 1–3 (безопасность, авторизация, персистентность,
  контракты — есть явный сигнал к строгому режиму), `light` для Фаз 0 и 4
  (документация и настройки качества), `light` для Фазы 5 на первом шаге с
  переходом в `strict` при изменении границы безопасности.
- **Полномочие:** AGENTS.md §42 (`Use automated tests for critical behavior`) и
  §87/§58 (Definition of Done) — проект уже требует тестов для
  security-critical поведения.
- **Правило:** RED → GREEN → REFACTOR только там, где решение `strict`.
  Никакой шаг не считается сделанным без прогона, который мог бы упасть.

## 4. Критерий готовности к церемонии

Церемонию можно проводить, когда одновременно верно:

- [ ] Б1 закрыт: seed загружается и активируется кодом, а не документацией
- [ ] Б2 закрыт: `Critical` выполняется с подтверждением и TOTP, без них — нет
- [ ] Б3 закрыт: ум переживает рестарт
- [ ] Б4 закрыт: подтверждение делается из Windows-клиента
- [ ] Б5, Б6 закрыты: документы не противоречат ни коду, ни решениям владельца
- [ ] Все preflight-гейты пройдены на репетиции в копии БД
- [ ] Foundation и Desktop зелёные, e2e зелёный
- [ ] Бэкап снят и восстановление проверено в тот же день

Если хоть один пункт не выполнен — церемония откладывается. Рождение
необратимо, а `docs/genesis-ceremony.md` прямо предупреждает, что ложное
заверение о бэкапе — единственный незащищённый путь.

  аудита, повторно не инспектировались в этой сессии.
- Оценки сроков — ориентировочные, не обязательства.
